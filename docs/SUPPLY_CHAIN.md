# Supply-chain inventory and SBOM

NuiGraph creates two complementary CycloneDX documents for every verified build:

- `nuigraph-native.cdx.json` inventories the application, direct C++ libraries,
  the optional Nui framework and, when the binary exists on a Debian/Ubuntu
  host, the exact OS packages that own its dynamically linked libraries.
- `nuigraph-npm.cdx.json` is generated by npm from `package-lock.json` and
  includes the full frontend development dependency graph, integrity hashes,
  licences and distribution URLs.

Both documents record the full source commit and whether the checkout was dirty.
They contain dependency metadata, not application configuration, user content or
secret values. CI uploads the pair as `nuigraph-sbom-<commit>` for 30 days after
all tests pass. A production deploy also installs the pair read-only under the
root-owned release directory at `/opt/nuigraph-studio/current/sbom/`.

## Generate and validate locally

Build first so the native inventory can resolve the final binary's shared
libraries, then run:

```bash
node scripts/generate_sbom.mjs build/sbom
bash tests/check_sbom.sh
```

Generation requires Node/npm, `pkg-config`, Git and the native dependencies used
by the build. `ldd` plus `dpkg-query` enrich the result on Ubuntu; if they are not
available, the direct C++ dependency inventory is still generated. npm reads the
lockfile with `--package-lock-only` and does not need to execute package scripts.

The validation gate checks CycloneDX structure, unique component references,
dependency edges, source commit metadata, the required native components, a
plausible locked npm graph and the absence of configuration-secret names. It
also rejects a semver Nui tag: the reviewed `v3.5.0` source is pinned to upstream
commit `547f34d694acfae7abf802733273113fcacddc98`.

## Upgrade procedure

1. Resolve the desired upstream Nui release to its full commit using the
   authoritative repository and review the diff from the current commit.
2. Update the CMake pin, generator and validator together. Never replace the pin
   with a branch, short hash or release tag.
3. Regenerate both SBOMs, run npm audit, build both frontend modes where the
   Emscripten SDK is available, and run all CTest suites.
4. Review unexpected component additions, removed integrity hashes, licence
   changes and new native shared libraries before merging.
5. After push, retain the CI SBOM with the release evidence and compare it with
   the read-only copy installed by deploy.

## Trust and limitations

An SBOM is an inventory, not proof that a component is safe. The current files
are not signed and the build has no SLSA provenance or reproducibility claim.
GitHub artifact access and root-owned release permissions protect normal access,
but they do not survive a compromised CI account or root host. Signed provenance
and independent verification therefore remain roadmap work.

The native inventory describes the environment that produced the binary. A
different host can legitimately record different Ubuntu package revisions. The
npm inventory includes development and platform-optional packages because they
are part of the locked build graph even when they are not shipped to browsers.
The repository also has no declared project licence; choose and add one before
public distribution rather than inferring a licence from dependencies.
